# 계약 진화와 출처 증명 설계

[English](contract-evolution.md) | [한국어](contract-evolution-ko.md)

> 영어본의 한글 번역이다. 내용이 다르면 영어본을 기준으로 한다.

현재 FX5와 R Neutral IR은 `schema_name`, 버전, JSON Schema `$id`가 같지만
커밋된 스키마 바이트와 finding 열거형이 다르다. 소비자는 먼저 설치 패키지와
정확한 프로필 식별자를 선택한 뒤 검증해야 한다. `$id` 또는 버전만 같다는
이유로 다른 프로필 스키마를 적용할 수 없다. 기존 스키마 파일과 IR 출력은
이 설계 문서로 변경되지 않는다.

## 향후 스키마 식별

권장 계약은 프로필과 계약 개정마다 서로 다른 불변 `$id`를 부여하고 패키지,
프로필 ID, 계열, 스키마 SHA-256, 호환 producer 버전을 매니페스트에 기록하는
것이다. 소비자는 정확한 매니페스트 튜플을 요구하고 알 수 없는 튜플은
거부한다. 대안으로 공통 기본 스키마와 프로필별 오버레이, 또는 조건부
분기를 둔 단일 스키마가 있다. 두 대안은 구성 요소가 늘고 한 프로필의
변경이 다른 프로필을 의도치 않게 넓힐 위험이 있다. 이행 전에 모든
소비자를 조사하고 변환 어댑터를 제공하며 기존/신규 선택과 교차 프로필
거부를 시험하고 호환성 영향을 검토한다. 1.0.0 데이터를 묵시적으로
재해석하지 않는다.

## 빌드와 증명

빌드 매니페스트에는 깨끗한 원본 commit/tree, 고정한 빌드 도구 버전,
압축 파일 해시, `published: false`가 들어간다. 설치 검증은 리소스 출처와
import 경로를 확인한다. 향후 증명은 이 값과 의존성 잠금 해시, CI 실행기
식별자, 시험 보고서, 압축 파일 내부 항목별 해시를 결속할 수 있다.
압축 파일 전체 해시와 내부 항목 해시는 서로 다른 비교다. 압축 메타데이터가
다르면 비트 동일 빌드라고 주장하지 않는다. 서명이나 공개 전에 증명 형식,
신뢰 발행자, 키 보관, 검증 정책, 릴리스 승인을 정해야 한다. 이 문서는
서명자나 릴리스 절차를 확정하지 않는다.

## 모듈 경계

ZIP/SQLite/XML 방어는 설치된 각 프로필 패키지에, GXW OLE 제한은 GXW
패키지에 둔다. 큰 디코더를 나중에 분리할 때는 공개 import와 CLI 진입점,
스키마와 리소스 바이트, opcode 표, 출력 순서를 보존해야 한다. 안정적인
내부 인터페이스를 먼저 정하고 모든 지원 플랫폼에서 설치 wheel 출력을
고정된 비공개 기준 및 합성 부정 사례와 대조한다. 이번 작업은 큰 모듈
분할을 포함하지 않는다.
